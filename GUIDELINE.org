#+title: mono_player — Project Guideline
#+author: agustin
#+date: 2026-08-10

Native Wayland YouTube client. Qt Quick UI over libmpv; yt-dlp runs as
mpv's ytdl_hook subprocess. The differentiating feature is browser-style
*tabs* over a single player instance — no existing client has this.
Everything else (queue, feeds, subscriptions, search) exists elsewhere and
is deliberately built the boring way.

* Design principles

- The app is glue. All heavy work is delegated to code that already exists
  and is maintained by someone else: mpv decodes, yt-dlp extracts, sqlite
  persists, the compositor composites. Our code holds state and draws a UI.
- Never implement YouTube extraction. yt-dlp has hundreds of contributors
  and still suffers breakage days when Google moves; a solo project does
  not survive that race. If yt-dlp can't do it, the feature waits.
- Playback must never depend on login, and login must never be required.
  Two independent failure domains (see Architecture).
- Performance target: beat Chrome-on-YouTube on the same machine, measured,
  not assumed. We win by not doing work (no DOM, no telemetry, no JS
  buffering logic), not by micro-optimizing.

* Architecture

The account never touches playback:

#+begin_example
  PLAYBACK layer   mpv ytdl_hook (yt-dlp subprocess, anonymous)
                   + PO token provider -> libmpv
                   No account. Ever.

  BROWSE data      InnerTube anonymous: related videos, search, trending.
                   Logged out, this IS the whole browse experience.

  ACCOUNT layer    gpsoauth Bearer -> InnerTube (client ANDROID)
                   subscriptions/history/playlists only.
                   Never used for stream URLs.
#+end_example

If Google breaks PO tokens, the feed still loads. If auth breaks, videos
still play. One incident never takes down both.

** Login (decided: gpsoauth, not cookies)

- microG is Android-only; what we implement is the protocol microG speaks:
  device registration -> master token -> scoped Bearer tokens. The
  =gpsoauth= Python library does this and is maintained (Aurora Store
  proves the flow alive as of mid-2026).
- Cookies as the *session mechanism* were rejected: they expire, they
  entangle playback with the PO-token session binding, and reading a
  browser's cookie DB is fragile and invasive.
- QtWebEngine is allowed in exactly ONE place: the login screen, loaded on
  demand and torn down afterwards. An external browser can never hand the
  =oauth_token= cookie back to the app, so a minimal embedded webview is
  the only non-invasive path (it is what microG/Aurora do). Chromium never
  runs during browsing or playback; the performance premise holds.
- Flow, once per install: embedded webview -> accounts.google.com/EmbeddedSetup
  -> intercept =oauth_token= cookie -> =gpsoauth.exchange_token()= -> master
  token (=aas_et/...=) -> OS keyring. Then =perform_oauth()= mints ~1h Bearer
  tokens on demand; those are never persisted.
- 2FA accounts cannot password-login; the browser flow is the only path.
  Design that screen properly.

** SECURITY — non-negotiable, the lazy ladder does not apply here

- The master token grants the *entire* Google account. It lives in the
  Secret Service keyring via =keyring=. Never a file, never a log line,
  never telemetry, never an environment variable.
- Login is optional; every feature except sync works logged out. This is
  both ban mitigation (real account + unofficial client = flag risk) and
  the honest default.
- Input validation at the InnerTube parsing boundary: Google's responses
  change shape without notice; malformed data must degrade, not crash.

* UI model

** Tabs (the feature)

Three distinct structures — do not merge them:

| Structure   | Semantics                             | Lives in            |
|-------------+---------------------------------------+---------------------|
| Queue       | per tab, ordered, auto-advances       | sqlite; materialized into mpv playlist |
| Tabs        | parallel playback contexts            | local sqlite        |
| Watch later | persistent, unordered                 | YouTube =WL= playlist |

- A POOL of libmpv instances with a hard cap (decided 2026-08-11,
  superseding "one instance, always"): browser-grade tab switching needs
  a live, paused player per recent tab — switching is show/pause, not
  reload. Cap 3 live players (LRU evict) plus a 30-minute background TTL:
  browser-style tab discarding, so 20 open tabs never mean 20 decoders.
  A frozen tab stays in the strip; only its playback context
  ={queue: [video_id], queue_idx, position_secs}= survives (sqlite, as
  always), and returning to it re-materializes — through the
  resolved-URL cache when still valid. The RAM cost measured far below the
  estimate: 3 live players = 578MB avg / 681MB peak PSS vs 585/608 for
  one (paused players hold no growing buffers) — still under Chromium's
  819MB.
  Every queue lives in sqlite; a player's playlist is a materialization
  of ITS tab only — so queues survive restarts for free.
- Tab switch: persist =playback-time= + =playlist-pos= of the outgoing
  tab, then =loadfile <first> replace start=<pos>= plus =loadfile append=
  for the rest. =loadfile replace= clears mpv's playlist (man mpv 0.41) —
  here that is the mechanism, not a hazard.
- Sync is one-way. UI writes to mpv (=loadfile <url> append-play= is
  "enqueue", =playlist-move= is "play next"); only the =playlist-pos= and
  =playback-time= observers flow back into sqlite. mpv is never the
  source of truth.
- Browse (feed, channel, search) is ONE global view outside tabs; scroll
  position belongs to that view. Tabs hold playback, nothing else.
- Related videos are a function of =video_id=, not tab state: anonymous
  InnerTube =next= for the current video, LRU-cached like thumbnails
  (yt-dlp does not extract related). Click replaces the active tab's
  video; new-tab / enqueue via context menu. No per-tab history — YAGNI,
  add if it hurts.
- "Watch later" maps to the account's real =WL= playlist via InnerTube, so
  cross-device sync comes free. Tabs and queues are local; YouTube has no
  concept of them and nothing gets invented server-side.
- Mini-player / PiP is a Hyprland windowrule on the window title, shipped
  as a README snippet — not code:
  #+begin_example
  windowrulev2 = float, title:^(mono_player — mini)$
  windowrulev2 = pin,   title:^(mono_player — mini)$
  #+end_example

** Rendering

- Wayland has no foreign-window embedding: =wid=/=winId()= does NOT work.
  Video renders through =mpv_render_context= into a
  =QQuickFramebufferObject::Renderer= (see
  =mpv-examples/libmpv= for the reference Qt Quick integration). This is
  the robust path per mpv docs, and it makes the video a real QML item:
  tabs, overlays and animation compose naturally.
- Language split: the mpv<->Qt bridge is ONE C++ file (written once),
  registered as a QML type. The bridge OWNS the =mpv_handle=
  (=mpv_create=/=mpv_initialize=) and is the single mpv facade:
  =Q_INVOKABLE command()= / property get/set, Qt signals for observed
  properties (=playlist-pos=, =playback-time=) and log messages. Python
  and QML never touch libmpv directly; python-mpv is out. The bulk of the
  file is mechanical =QVariant= <-> =mpv_node= conversion.
  Everything else is Python/PySide6.
  Two hard-won render-API requirements live in the bridge: =vo=libmpv=
  must be set explicitly or the core opens its OWN Wayland window and
  the FBO stays black, and =MPV_RENDER_PARAM_WL_DISPLAY= (Qt's
  wl_display) must be passed at render-context creation or the vaapi
  interop cannot create a VA display and hwdec silently degrades to
  =vaapi-copy= (~2.3x the CPU). The =[vd]= log line in the QML filter
  is the permanent hw/sw decode tell.
  Python performance is irrelevant — there is no hot loop in our code; if
  a model ever janks, lowering that one model to C++ is a localized
  refactor, done after measuring, not before.
- Feed grid rules (these ARE the performance):
  - =GridView= with fixed =cellWidth=/=cellHeight= — zero relayout on load.
  - =Image { asynchronous: true; sourceSize.width: 320 }= — decode off the
    UI thread, AT display size (~350KB vs ~3.5MB per thumbnail in RAM).
  - Delegates hold data from the model only; no Python calls in bindings
    evaluated during scroll (GIL).
  - Measure with =QSG_RENDER_TIMING=1=; target <16ms frame time.

** Network (where we'd lose to Chrome if lazy)

- ONE =httpx.AsyncClient= app-wide: HTTP/2 multiplexing, pooled
  connections. A client per request costs a TLS handshake each time.
- Concurrency semaphore ~8 for thumbnails; more saturates, doesn't speed up.
- Disk LRU cache keyed by video id: scrolling back up = zero network.
- Fetch visible + =cacheBuffer= only; never prefetch a 200-item feed.
- Cold start: paint the cached feed from sqlite before any network — first
  content in ~200ms perceived, fetch continues behind it.
- Tab re-switch rides an in-memory cache of resolved stream URLs (what
  ytdl_hook wrote to =stream-open-filename=), valid until the googlevideo
  =expire== stamp minus a margin: 2.8s extraction on first play, ~0-0.9s
  on return. A stale cached URL error invalidates and retries once via
  the original page (=TabManager.loadFailed=).

* Format selection

Hardware verified on surface (i7-1185G7, Iris Xe / Gen12, iHD 26.2.4):
=VAProfileAV1Profile0= and =VP9Profile0..3= under =VAEntrypointVLD=.
End-to-end confirmed: real 4K60 AV1 from YouTube plays with
"Using hardware decoding (vaapi)".

- The yt-dlp format string is built at startup from probed VA-API caps and
  cached — never hardcoded. Extraction runs in mpv's ytdl_hook (subprocess),
  never in-process: the string is applied via mpv's =ytdl-format= property.
  Library-mode extraction (EDL pairing, expiry, retries — all ours) is the
  documented upgrade path only if error UX ever demands it; error surface
  today is =MPV_EVENT_LOG_MESSAGE= parsing. AV1 requested only where the silicon decodes
  it; software dav1d at 4K+ is a stutter generator, and blind AV1 requests
  would make us slower than Chrome on half the machines.
  #+begin_example
  current (AV1-first, re-preferred 2026-08-14 after 65 clean --stress cycles):
                bv*[vcodec^=av01][height<=?4320]+ba/bv*[vcodec^=vp9]+ba/b
  #+end_example
- 8K on an iGPU is "exposed" but bandwidth-bound; the practical ceiling on
  this hardware is 4K. Which ladders YouTube offers also depends on
  yt-dlp's =player_client= — expect that to shift when Google does.
- mpv config: =hwdec=auto-safe=. Embedded playback goes through the render
  API, whose only backends are OpenGL and SW (=render.h=, 0.41) — the vo is
  effectively =libmpv=; =vo=gpu-next= / =gpu-api=vulkan= do NOT apply to
  the embedded path. Qt must be pinned to the OpenGL RHI backend
  (=QQuickWindow.setGraphicsApi(OpenGL)=) or =QQuickFramebufferObject=
  breaks; vaapi interop rides EGL on Wayland. HDR
  (=target-colorspace-hint=) is *unverified* on Hyprland — test before
  listing it as a feature.

* Environment

- NixOS flake in this directory; =nix develop= gives PySide6, python-mpv,
  yt-dlp (as binary + PO token plugin, consumed by mpv's ytdl_hook — the
  Python library import is no longer part of the design), gpsoauth,
  keyring, httpx, libmpv headers + qtdeclarative (for the C++ bridge),
  nodejs (PO token provider), vainfo.
- Flake debts: none. =python-mpv= dropped, =qasync= + =h2= added
  2026-08-10 (qasync builds with its flaky GC tests skipped);
  QtWebEngine ships inside nixpkgs' pyside6 — only its QML plugin path
  needed adding to =QML_IMPORT_PATH= alongside qtdeclarative's.
- =keyring= needs a running Secret Service daemon (gnome-keyring);
  Hyprland does not provide one by itself. =check.sh= must assert it.
- =./check.sh= is the runnable environment check (AV1/VP9 hw decode,
  Python imports, libmpv headers, Wayland). Run it after any flake or
  system change.
- System-level VA-API comes from =nixos-config= —
  =hardware.graphics.extraPackages = [ intel-media-driver ]= in
  =modules/hardware/hardware.nix= (activated 2026-08-10). The
  =LIBVA_DRIVERS_PATH= in this flake's devShell is now redundant but
  harmless: same driver.

* Known debts and risks

- PO token provider: INTEGRATED 2026-08-10. nixpkgs'
  =bgutil-ytdlp-pot-provider= python package ships both the yt-dlp plugin
  (auto-discovered: it shares the env with yt-dlp's binary) and the built
  Node server (=share/.../build/main.js=). =main.py= starts the server on
  launch (skipped if port 4416 is already serving) and terminates it on
  quit; =check.sh= asserts plugin + node + main.js. Verified: yt-dlp
  reports =bgutil:http= as an active provider and generates gvs PO tokens
  through it. Still open for release: the bundle-vs-require packaging
  story (a "native" app shipping Node remains ugly).
- iHD driver race (found 2026-08-11, repro: =main.py --stress=): with
  zero-copy vaapi, tab-switch decoder teardown segfaults inside
  =iHD_drv_video.so= while mpv's render thread maps an in-flight frame
  (=vaSyncSurface= in =mapper_map=). AV1 hits it fastest but VP9 crashed
  too. Mitigated app-side, not fixed: =stop= then a 150ms drain before
  materializing loadfiles (=TabManager=). 2026-08-14: AV1-first re-tested
  with the drain in place — 65 stress cycles clean (crash-at-3 baseline),
  driver still 26.2.4, so the drain alone suffices; AV1 re-preferred, the
  VP9-first belt removed. =MONO_HWDEC=vaapi-copy= is the fully stable
  fallback (~2.3x decode CPU). Re-run =--stress= after any
  intel-media-driver or mpv bump.
- SABR/UMP: YouTube is moving stream delivery to a server-driven binary
  protocol; yt-dlp's SABR downloader was still in test mid-2026. This is
  yt-dlp's problem by design, but expect playback breakage windows.
- gpsoauth is reverse-engineered; Google can break the flow. Aurora Store
  breakage is the canary — if Aurora falls, we fall.
- ToS: this client violates YouTube ToS like every client in this space
  (youtube-dl DMCA 2020, Invidious C&D 2024, NewPipe never in Play Store).
  Distribution via a store should assume takedown risk.
- InnerTube =browse= responses are undocumented and shape-shift; parsing
  must be defensive and versioned.
- Home DECIDED (2026-08-11): logged in, home is the account's
  personalized feed (=FEwhat_to_watch=, ANDROID + Bearer — serves
  =gridVideoRenderer=; loaded on launch behind the session restore), with
  =gh/gs/gy/gp/gw= jumping to home/subscriptions/history/playlists/watch
  later. Logged out, home stays the last cached feed + search — the
  anonymous-home story (trending died mid-2025) remains unbuilt until
  someone logged-out asks for it. Shorts have no parseable dedicated
  feed (elementRenderer protobufs), but the ones inside the normal feeds
  are parsed since 2026-08-24: =reelItemRenderer= and
  =shortsLockupViewModel= map to the same =Video= as any other item, in
  feed order, with duration ="SHORT"= (they carry none) -- playback needs
  nothing special, the id is a normal watch id.

* Status / next steps

Closed: platform (Wayland-only, Hyprland), rendering path (render API =
OpenGL only, Qt pinned to GL), language split, login mechanism (gpsoauth
via login-only webview), data model (queue per tab, sqlite as source of
truth, browse global outside tabs), extraction (mpv ytdl_hook, not
library), format policy, dev environment. All hardware and environment
checks pass as of 2026-08-10.

=mpv_handle= ownership decided: C++. The bridge creates and owns the
handle and is the only code that links libmpv (see Rendering). Python
drives mpv through the bridge's invokables/signals; python-mpv leaves
the flake.
